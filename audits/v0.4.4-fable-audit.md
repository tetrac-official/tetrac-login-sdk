# Security Audit — `@tetrac/login-sdk` (branch `v0.4.5`, HEAD)

**Date:** 2026-07-03
**Target:** `@tetrac/login-sdk` — non-custodial auth + wallet-encryption SDK
**Branch / commit context:** working branch `v0.4.5`; `package.json` version `0.4.5`. Audit covers HEAD
including the not-yet-released 0.5.0-track UI (`src/ui/passkey.ts`, `src/ui/LoginPanel.tsx` hardware-wallet
toggle, `src/ui/EmailMethod.tsx` passkey generator) that already lives in the tree.
**Authoritative docs consulted:** [`docs/CRYPTO_SPEC.md`](../docs/CRYPTO_SPEC.md),
[`docs/THREAT_MODEL.md`](../docs/THREAT_MODEL.md), [`docs/LEDGER_SUPPORT_PRD.md`](../docs/LEDGER_SUPPORT_PRD.md).
Governing rule: **the code is authoritative — if code and doc disagree, the doc is the bug.**

---

## 0. Scope & method

**Scope.** The client SDK (`src/client`, `src/core`, `src/react`), the server routes and storage adapters
(`src/server`, `src/storage`, `src/next`), the Ledger hardware-wallet path (`src/ledger`), and the
UI panels (`src/ui`). Design invariants were read from the three docs above; every finding is grounded in
`file:line` evidence at HEAD (`v0.4.5`), not against a generic "SDK of this class."

**Method.** Multi-agent sweep: 10 parallel finders each owning a subsystem (crypto/KDF, auth/session,
WebAuthn/biometric, Ledger/off-chain, server routes/rate-limit, storage, UI reveal/clipboard, build/exports,
supply-chain, docs↔code), plus a completeness critic that re-derived the domain-separation and app-key
invariants from `CRYPTO_SPEC`/`LEDGER_SUPPORT_PRD` to catch gaps the finders missed. Every candidate was then
put through a **batched skeptical adversarial verification** pass: each finding was re-checked against HEAD,
tested against the accepted residuals in `THREAT_MODEL.md` (R1–R6) and the integrator obligations (§5), and
either confirmed with quoted code or dismissed as NOT-A-BUG / already-mitigated / delegated. Findings that
were the same root issue seen from different angles were merged (see F1, F2). Prior reconciliations in
[`v0.3.2-PRD.md`](./v0.3.2-PRD.md) and [`opus-4.8-comprehensive-audit.md`](./opus-4.8-comprehensive-audit.md)
were treated as settled and not re-litigated.

**Bottom line.** The cryptographic core is sound: `@noble/hashes` + Web Crypto only (no `crypto-es`, no CBC,
no `Math.random`), authenticated AES-256-GCM with fresh 96-bit IVs, 600k-default PBKDF2 pinned per user,
memory-only app key, server-minted single-active-session tokens, atomic single-use challenges, and correct
appId domain separation on the software wallet and PBKDF2 paths. **There are no findings against the
email/passkey, biometric, session, or software-wallet crypto that are exploitable within the threat model.**
The two genuinely serious items are both in the **hardware-wallet (Ledger) path**, are **not
attacker-triggered**, and both cause **silent, permanent loss of funds** in embedded wallets — and the
project's own `LEDGER_SUPPORT_PRD.md` already specifies the fix and calls the shipped shape a "fund-loss
landmine." Everything else is low/info hardening.

## 1. Executive summary

| Severity | Count |
|----------|------:|
| Critical | 0 |
| High     | 2 |
| Medium   | 1 |
| Low      | 12 |
| Info     | 6 |
| **Confirmed total** | **21** |

Additionally, **25** candidate findings were investigated and dismissed as not-a-bug / already-mitigated /
delegated-to-integrator (Appendix A).

**Headline risks (both hardware-wallet, both non-attacker, both permanent fund loss):**

1. **F1 (high) — HW app key is derived straight from the Ledger signature with no recovery wrap.** A routine
   Ledger firmware/adapter update changes the accepted Solana off-chain envelope, which changes the
   signature bytes, which changes `SHA-256(hex(sig))`, which changes the AES app key — and every embedded
   wallet becomes permanently undecryptable. The `LEDGER_SUPPORT_PRD` §4 recovery wrap that was designed to
   prevent exactly this is **entirely unimplemented** at HEAD.
2. **F2 (high) — the HW-vs-SW app-key message variant is a client boolean that is never persisted
   server-side.** Registering with `hardwareWallet:true` but later revealing/logging in with it `false` (or
   an integrator wiring `LoginPanel`'s toggle and `ExportKeyPanel`'s prop inconsistently) derives the *other*
   message's key. Auth still succeeds; decryption silently fails; the user is locked out of their own funds.

Both are latent time-bombs the SDK ships as a first-class public API (`hardwareWalletToggle` /
`hardwareWallet`) despite the PRD stating "no key-from-signature-only accounts ever exist." The remaining
items are avoidable-lockout edges and defense-in-depth hardening.

## 2. Findings (ranked)

### F1 — Hardware-wallet app key is derived directly from the Ledger signature with no recovery wrap; a routine firmware/adapter upgrade silently and permanently orphans all embedded wallets — HIGH

**Severity:** High (permanent fund loss; non-attacker trigger; HW-wallet accounts only)
**Category:** crypto / key-management
**Locations:**
- `src/client/authClient.ts:275-283` (walletHandshake derivation)
- `src/client/authClient.ts:124-130` (reveal/unlock re-derivation)
- `src/core/crypto.ts:39-41` (`deriveAppKeyFromSignature`)
- `src/ledger/solanaSigner.ts:82-97` (envelope cascade)
- `src/core/offchainMessage.ts:174-183` (candidate ordering)
- `docs/LEDGER_SUPPORT_PRD.md:91-96, 246-251, 321-323` (mandated, unimplemented mitigation)

**Attacker + impact.** *No attacker required.* A Ledger user registers/connects an account today; their
embedded wallet secrets are encrypted under `SHA-256(hex(current-envelope-signature))`. On any later Ledger
firmware update, wallet-adapter update, or host switching the signing path (e.g. legacy→v0 off-chain
envelope), the device signs a **different preimage**, produces **different signature bytes**, and the client
re-derives a **different app key**. Because auth is envelope-tolerant (the server tries every candidate), the
user still **logs in fine** — but every embedded (SDK-generated) wallet is now cryptographically bricked.
Non-custodial + no server-side plaintext + no recovery wrap = **irreversible loss of all funds** in those
wallets. This is *not* the accepted `THREAT_MODEL` R2 residual: R2 is losing the authenticator; here the user
still holds the Ledger and a routine vendor update orphans the vault.

**Evidence.**
```ts
// authClient.ts:275-283 — HW app key = SHA-256(hex(sig)) over the envelope-wrapped signature
const keyMessage = hardwareWallet
  ? walletAppKeyMessageHw(this.config.appId)
  : walletAppKeyMessage(this.config.appId);
const keySig = await signMessage(enc.encode(keyMessage));
return { appKey: deriveAppKeyFromSignature(bytesToHex(keySig)), signatureHex: bytesToHex(authSig), challenge };
```
```ts
// core/crypto.ts:39-41 — the app key is literally the hash of the signature, no wrap, no master key
export function deriveAppKeyFromSignature(signatureHex: string): string {
  return bytesToHex(sha256(utf8ToBytes(signatureHex)));
}
```
```ts
// ledger/solanaSigner.ts:82-93 — signMessage does NOT sign raw bytes: it cascades over off-chain envelopes
for (const envelope of candidates) {
  try { return assert64(await deps.signOffchainMessage(deps.path, envelope)); }
  catch (err) { const msg = ...; if (!msg.includes("0x6a81")) throw err; }
}
```
`offchainMessage.ts:179-182` orders the candidates `[encodeOffchainMessageLegacy(...), encodeOffchainMessage(...)]`
(legacy 20-byte header first, then v0 85-byte header). The two envelopes are distinct ed25519 preimages, so
they yield distinct signatures and distinct app keys. The auth path tolerates this
(`verifySolanaSignature` tries every candidate, `signature.ts:50-52`); the **app-key path has no such
fallback** — `deriveAppKeyFromSignature` runs exactly once on whatever the device emitted.

**Mandated-but-missing mitigation.** `LEDGER_SUPPORT_PRD.md:248-251` states: *"Shipping a key-from-signature
path with no recovery factor would create a fund-loss landmine that detonates on a routine Ledger firmware
update. The recovery wrap is therefore mandatory, not optional, for HW accounts,"* and §9 (`:321-323`): *"HW
accounts are created with the recovery factor mandatory (no key-from-signature-only accounts ever exist)."*
A repo-wide grep for `wrapSig | wrapRec | ttc-hw-wrap | keyMsgVersion | hwAccount | master | signEncoding`
across `src/` returns **zero matches** — PRD Part 2 is entirely unimplemented, yet `LoginPanel.tsx:58-78`
ships the `hardwareWalletToggle`/`hardwareWallet` public API and `WalletMethod.tsx:43-47` threads it into
`connectWallet`, so integrators can and will create exactly the "key-from-signature-only" accounts the PRD
says must never exist.

**Fix.** Implement `LEDGER_SUPPORT_PRD` §4.2: at HW registration generate a random 32-byte `master`, encrypt
the wallet bundle under `master`, wrap `master` under `kdk = HKDF-SHA256(SHA-256(keySig), info="ttc-hw-wrap-v1")`
as `wrapSig`, **and** under an independent recovery KEK (biometric-unlock KEK or a downloadable recovery code)
as `wrapRec`; store both wrap blobs + a `keyMsgVersion`/`hwAccount` flag on `UserData`. On login, unwrap via
`wrapSig`; on failure (envelope drift) fall back to `wrapRec` and silently re-wrap under the new signature.
Until that lands, **hide/disable the HW toggle and reject `hardwareWallet:true` in `authClient`**, or at
minimum pin the accepted envelope version per account and disable the cascade for the app-key signature so
the preimage is frozen at registration.

### F2 — Hardware-vs-software app-key message variant is a client-supplied boolean, never persisted or echoed server-side; an inconsistent flag at login/reveal derives the wrong key and silently locks the user out of funds — HIGH

**Severity:** High (permanent lockout of embedded wallets; non-attacker trigger; wallet accounts)
**Category:** crypto / protocol-logic
**Locations:**
- `src/client/authClient.ts:275-277` (handshake variant select) and `authClient.ts:124-130` (reveal/unlock select)
- `src/core/index.ts:29-31` (`walletAppKeyMessage`, newline form) vs `src/core/index.ts:44-50` (`walletAppKeyMessageHw`, newline-free form)
- `src/core/types.ts:39-63` (`UserData` — no `hwAccount`/`keyMsgVersion` field)
- `src/server/routes.ts:288-301, 423-437` (register/connect store no HW marker)
- `src/ui/LoginPanel.tsx:58-78` (uncontrolled toggle) and `src/ui/WalletMethod.tsx:43-47`, `src/ui/ExportKeyPanel.tsx:171-190` (independent `hardwareWallet` prop)

**Attacker + impact.** *No attacker required — an ordinary integrator refactor triggers it.* A Web3 account's
app key is `SHA-256(hex(sig))` over **one of two distinct preimages** chosen solely by the client
`hardwareWallet` boolean: `walletAppKeyMessage(appId)` (contains `\n\n`) or `walletAppKeyMessageHw(appId)`
(newline-free ASCII). These are different byte strings → different signatures → different app keys. The server
stores **nothing** about which variant an account used, and the auth signature it verifies
(`walletLoginMessage(challenge)`) is identical for both — so login/connect **always succeeds** regardless of
the flag, and only the encryption key silently differs. A user who registers with the toggle ON but later
reveals/logs in with it OFF (or vice-versa), a connector build that stops reporting `hardwareWallet`, a
software reconnect of the same physical wallet, or an integrator who wires `LoginPanel`'s toggle and
`ExportKeyPanel`'s `hardwareWallet` prop from different sources, all derive the *other* key: the user appears
logged in, then hits an inexplicable decrypt failure. Combined with **F1** (no recovery wrap) the lockout is
unrecoverable. This is a distinct mechanism from F1 (mis-selected message from an unpinned flag, *no* firmware
change needed).

**Evidence.**
```ts
// authClient.ts:275-277 (handshake) and 125-127 (reveal/unlock) — same fork on a client boolean
const keyMessage = hardwareWallet
  ? walletAppKeyMessageHw(this.config.appId)   // "…trust. Only sign…"  (no newline)  core/index.ts:44-45
  : walletAppKeyMessage(this.config.appId);    // "…trust.\n\nOnly sign…" (newline)    core/index.ts:19-20
```
`UserData` (`types.ts:39-63`) records `authMethod` but **no** hardware flag and **no** `keyMsgVersion`; grep
for `hardwareWallet | keyMsgVersion | hwAccount` across `src/server` and `types.ts` returns nothing.
`LoginPanel.tsx:61-63` seeds an uncontrolled toggle (`useState(() => defaultOn ?? hardwareWallet ?? false)`)
while `ExportKeyPanel.tsx:178` reads an independent prop (`doReveal({ signMessage, hardwareWallet })`) — no
shared source of truth. `connectWallet` never overwrites a returning wallet's stored blobs
(`routes.ts:431-437`, guarded by `!user.wallets?.length`), so a mismatched flag makes auth succeed while
decrypt fails.

The project's own `LEDGER_UI_SUPPORT_PRD` (dated 2026-06-30, verified on a real Ledger) reproduces exactly
this: login-HW then reveal-SW yields *"Re-authentication failed — wrong credentials,"* and flags the missing
server-side `keyMsgVersion` pinning as the fix. `CRYPTO_SPEC.md §7` does **not** document a HW-consistency
integrator obligation, so this is not a delegated residual.

**Fix.** Persist the variant server-side at register (e.g. `keyMsgVersion: 'sw' | 'hw-ascii'` on `UserData`)
and return it from `/challenge` — mirroring how `pbkdf2Iterations` is already echoed for email accounts
(`authClient.ts:236-243`) — so the client always re-derives with the exact message the account was created
with, never trusting a per-call UI toggle. Until then, derive-and-validate (decrypt a known wallet blob)
before treating a wallet login as successful, and surface a distinct *"wrong hardware-wallet setting"* error
instead of the generic decrypt failure so a mismatch is diagnosable.

> **Relationship to F1.** F1 and F2 both stem from the same architectural gap — the HW app key is
> signature-derived with no server-persisted binding or recovery factor. F1 is drift of the *signature* under
> a fixed flag (firmware/envelope); F2 is drift of the *flag* under a fixed device (UI/integrator wiring).
> The `keyMsgVersion`/`hwAccount` persistence + recovery wrap in `LEDGER_SUPPORT_PRD` §4 closes **both**.

### F3 — `enableBiometricUnlock` orphans a previous credential's wrapped app-key blob (and gate secret) at rest, surviving disable/logout — MEDIUM

**Severity:** Medium (at-rest wrapped app key survives an invariant that promises it is gone; device-present + old-biometric attacker)
**Category:** exposure / cleanup-invariant
**Locations:** `src/client/biometricUnlock.ts:171-185` (enable), `src/client/biometricUnlock.ts:209-234`
(purge / clearSession hook), `src/client/webauthn.ts:202-219` (fresh credentialId per enroll),
`src/react/useBiometricUnlock.ts:100-109`

**Attacker + impact.** `enableBiometricUnlock()` registers a **brand-new** passkey each call
(`registerPasskey` → fresh `credentialId`, `webauthn.ts:71-72,99`), wraps the current app key keyed by that
new id (`wrapAppKey → blobPut`), and overwrites only the single-valued `MARKER_KEY` (`biometricUnlock.ts:183`)
— it never reads or deletes any prior credential's blob. `purge()` and the logout `clearSession` hook resolve
the credentialId **solely** from the current marker (`:215-219`, `:225-234`). So if enrollment runs a second
time (re-enable after a decline, a second authenticator, a UI double-tap, a retried flow), the **first**
credential's `UnlockBlob` — real AES-GCM ciphertext of the account app key — and, in gate mode, its
non-extractable-key-wrapped gate secret, remain in IndexedDB **permanently**, unreferenced by any marker,
purged by neither disable nor logout. This silently violates the module's stated at-rest guarantee
(`biometricUnlock.ts:13-17, 198-205`; `hasBiometricUnlock()` reports `false` while a live wrapped copy
persists). On a shared or later-compromised device, an attacker who can satisfy the OLD platform credential's
biometric assertion recovers the account app key (which decrypts every wallet and reconstructs the ed25519
auth identity), *after* the user believes unlock is disabled.

**Evidence.**
```ts
// biometricUnlock.ts:180-184 — wrap under the NEW credentialId, overwrite marker, no delete of the old blob
await wrapAppKey(registration.credentialId, secret, appKey);
...
if (hasWindow()) localStorage.setItem(MARKER_KEY, registration.credentialId);
```
```ts
// biometricUnlock.ts:216-219 — purge only ever touches the single marker credentialId
if (hasWindow()) localStorage.removeItem(MARKER_KEY);
await blobDelete(credentialId);
await gateDelete(credentialId);
```

**Why medium not high.** Unwrapping the orphan still requires a **fresh UV biometric assertion** behind a
non-extractable / HKDF-gated key (matches T13/T8), so a storage-scraping XSS cannot use it — the residual is a
device-present attacker who can satisfy the old credential's assertion. UV-gating caps this at medium.

**Fix.** Before overwriting `MARKER_KEY`, read the existing marker and, if it differs,
`purge(oldCredentialId)` (`blobDelete` + `gateDelete`) first. Additionally, make disable/logout clear the
**entire** `unlock_blobs` and `gate_secrets` stores (or track all enrolled credentialIds) so an orphan from a
crashed/aborted enroll cannot survive.

### F4 — `AuthClient.unlock()` arms the derived app key WITHOUT validation when `validateWith` is omitted — LOW

**Severity:** Low (footgun; wrong key armed as "authenticated"; no secret leak)
**Category:** auth
**Locations:** `src/client/authClient.ts:150-160`, `src/client/session.ts:215-220`

**Attacker + impact.** `unlock(creds, validateWith?)` only decrypt-checks the derived key when a `validateWith`
wallet is passed; otherwise it calls `armAppKey(appKey)` on whatever `deriveAppKey` produced, and `armAppKey`
sets `vault.memoryAppKey` unconditionally (`session.ts:215-216`). The hosted React path is safe
(`useAuth().unlock` passes `user?.wallets?.[0]`, `useAuth.ts:43`), but `AuthClient.unlock` is a documented
public API: a direct consumer calling `client.unlock(creds)` with no wallet to validate against gets a vault
that reports "authenticated" while holding a possibly-wrong app key. Every subsequent decrypt/sign silently
fails, and for the passkey path a wrong-but-plausible passkey is accepted as if valid — turning a typo into a
confusing locked-out state instead of an immediate "wrong credentials."

**Evidence.**
```ts
// authClient.ts:151-159 — armAppKey runs even when validateWith is undefined
const appKey = await this.deriveAppKey(creds);
if (validateWith) {
  try { await decryptWalletSecret(validateWith, appKey); }
  catch { throw new Error("Re-authentication failed — wrong credentials"); }
}
armAppKey(appKey);
```

**Fix.** Require a `validateWith` wallet (or pull one from the current session/user record) before arming and
refuse to arm if none is available; defaulting `validateWith` to a stored wallet blob would close this with no
API change.

### F5 — Passkey unlock/reveal re-derivation trusts only the client-cached PBKDF2 count with a silent 100k fallback (avoidable lockout) — LOW

**Severity:** Low (recoverable-but-avoidable lockout; no fund loss)
**Category:** crypto
**Locations:** `src/client/authClient.ts:116-123`, `src/client/session.ts:291-297`, `src/client/authClient.ts:234-244`

**Attacker + impact.** `loginWithEmail` self-heals the PBKDF2 iteration count from the server's `/challenge`
response (`pbkdf2Iterations ?? 100_000`, `authClient.ts:242`). But the re-auth path `deriveAppKey({passkey})`
— used by both `unlock()` and `revealSecret()` — reads the count **only** from localStorage via
`getPbkdf2Iterations()` with a silent 100k fallback (`authClient.ts:121`); `getPbkdf2Iterations()` returns
`null` when `ttc_pbkdf2_iter` is missing/non-numeric (`session.ts:291-297`). If that marker is evicted/cleared
(private-mode eviction, storage partitioning, partial wipe) while re-auth is attempted, a 600k-pinned account
re-derives at 100k → wrong app key → reveal fails and unlock arms a bad key — despite a correct passkey. The
server *does* know the real count, so this is avoidable.

**Evidence.**
```ts
// authClient.ts:121-122 — re-auth reads only the local marker, never the authoritative server value
const iterations = getPbkdf2Iterations() ?? 100_000;
return deriveAppKeyFromPasskey(creds.passkey, email, iterations, this.config.appId);
```

**Fix.** Have the re-auth passkey path consult the server-pinned count (fetch via the same challenge endpoint,
or thread the login-time value into the client), preferring the server value on disagreement; keep the local
value as a fast-path cache only.

### F6 — Client login silently falls back to 100k PBKDF2 when the server omits `pbkdf2Iterations`, orphaning 600k/1M accounts (availability) — LOW

**Severity:** Low (availability/correctness; **not** a stored-key downgrade)
**Category:** crypto
**Locations:** `src/client/authClient.ts:242-243`, `src/server/routes.ts:210-213`

**Attacker + impact.** `loginWithEmail` derives with `const iterations = pbkdf2Iterations ?? 100_000;`
(`authClient.ts:242`), where the value comes from `user?.pbkdf2Iterations` on the challenge response
(`routes.ts:213`). If the field is absent — a legacy account registered before pinning, an `undefined` record,
or the field stripped in transit — the client derives with 100k against a 600k/1M account, producing a
non-matching auth key (401) and an app key that cannot decrypt wallets, surfacing as a generic "Invalid
credentials" rather than a diagnosable mismatch. This is **not** a brute-force downgrade: the stored
`authPublicKey`/ciphertext were derived from the correct count and are unchanged; a wrong-count derivation
simply *fails*. The in-transit strip needs broken TLS (out of scope per `THREAT_MODEL §2`); the
legacy/undefined-record trigger is a genuine in-code edge.

**Evidence.** `authClient.ts:242` `const iterations = pbkdf2Iterations ?? 100_000;` — the fallback is
unconditional and indistinguishable from a legitimately-legacy 100k account.

**Fix.** Fail closed: if an account is known to exist but `pbkdf2Iterations` is missing, surface an explicit
error rather than defaulting to 100k, or have the server always echo the pinned count (defaulting stored
`undefined` to the documented legacy 100k at write time so the value is never absent for a real account).

### F7 — Re-enabling biometric unlock orphans the previous credential's wrapped blob + gate secret (React-hook path) — LOW

**Severity:** Low (cleanup-invariant violation; storage-scraping XSS cannot exploit)
**Category:** exposure
**Locations:** `src/client/biometricUnlock.ts:171-185`, `:209-234`; `src/react/useBiometricUnlock.ts:100-109`

**Attacker + impact.** The React `useBiometricUnlock` hook overwrites the single `REG_KEY`
(`useBiometricUnlock.ts:104-106`) with **no `isEnabled` guard** before re-enabling, and the underlying
`enableBiometricUnlock` always mints a fresh credentialId (F3). A second enable (re-enable / UI double-tap)
therefore permanently orphans the first credential's `UnlockBlob` and gate secret, which survive logout and
disable, violating the stated contract (`webauthn.ts:251` "leaves no recoverable secret behind";
`biometricUnlock.ts:200` "the at-rest blob is gone"). Exploitability is limited: unwrapping still requires a
fresh WebAuthn assertion for the orphaned credential, so a pure storage-scraping XSS (T8) cannot unwrap it —
the realistic adversary is device+biometric or later recovery of the old credentialId.

> **Note.** F3 and F7 are the *same orphaned-blob root cause* observed at the core-module and React-hook
> layers respectively; kept distinct only to record both entry points. The F3 fix (purge the old marker before
> re-enrolling, and add an `isEnabled` guard in the hook) closes both.

**Fix.** Add an `isEnabled` guard in the hook and purge the prior credential (`blobDelete` + `gateDelete`)
inside `enableBiometricUnlock` before writing the new marker/REG; or enumerate and clear the `unlock_blobs`
store on disable.

### F8 — Idle auto-lock timer cannot fire in a frozen/backgrounded tab; the lazy `isLocked()` safety net does not notify subscribers — LOW

**Severity:** Low (defense-in-depth; only under `lockOnHide:false` integrator opt-out)
**Category:** auth
**Locations:** `src/client/session.ts:182-187`, `:256-263`, `:136-173`

**Attacker + impact.** `scheduleLock()` uses `setTimeout` (`session.ts:186`), which browsers pause in
frozen/bfcached/backgrounded tabs, so the idle deadline can pass without `lockVault()` firing. `isLocked()`
(`:256-263`) lazily expires via `clearKeyState()` (`:259`, comment "silent — the scheduled timer fires the
notify"), but `clearKeyState()` (`:190-194`) never calls `notify()`, so no lock subscriber is notified until
the next use-path call. The proactive `bindHideHandler` handlers (`:136-173`) gate on `vault.lockOnHide`
(`:142,146`), so with `lockOnHide:false` (an integrator opt-out) they no-op and the memory app key stays armed
past `autoLockMs` in a backgrounded tab, widening the XSS-while-unlocked window (R1/T8). **Not exploitable on
defaults** (`lockOnHide:true` drops the key on hide/freeze/pagehide).

**Fix.** When `lockOnHide` is false, still drop the key on `visibilitychange→hidden` (or re-check the deadline
on `→visible`); alternatively have the lazy expiry in `isLocked()` call `notify()` when it clears a
previously-armed key.

### F9 — IP-leg rate-limit counter is not scoped by endpoint or appId — one shared 10/60s bucket per IP across all endpoints and all tenant apps — LOW

**Severity:** Low (availability / cross-tenant isolation; only under `trustProxyHeaders:true` opt-in)
**Category:** dos
**Locations:** `src/server/rateLimit.ts:20`, `src/server/routes.ts:106-121`, `src/core/config.ts:172-175`

**Attacker + impact.** With `trustProxyHeaders:true`, the IP leg passes `clientIp(...)` **raw** to
`checkRateLimit`, which builds the key `${prefixes.rateLimit}${identifier}` = `ratelimit:{ip}` with **no**
endpoint and **no** appId segment (`rateLimit.ts:20`) — unlike the per-target legs which pass
`challenge:${appId}:${id}` etc. With the default `rateLimit { windowSeconds:60, maxAttempts:10 }`, every
request from an IP shares one 10/60s budget across all endpoints and all tenant apps. All users behind one
NAT/corporate egress/CGNAT share a single 10/min bucket, and in a shared-Redis multi-tenant deployment app A's
traffic drains app B's budget for the same IP — a shared-IP lockout / cross-tenant isolation gap. A normal
login is 2 requests, so ~5 logins/min per egress IP exhausts it.

**Why low.** Fires only under the `trustProxyHeaders` opt-in (default false); per-target appId-scoped buckets
remain the primary, correctly-isolated protection (the `routes.ts:96-105` comment documents the IP leg as a
coarse secondary defense); and `THREAT_MODEL` R4 + obligation §5.3 delegate real volumetric/edge limiting to
the integrator.

**Fix.** Scope the IP leg like the per-target leg (`${endpoint}:${appId}:${ip}` or at least `${appId}:${ip}`)
and give the coarse IP throttle a separate, much higher ceiling than the per-target buckets.

### F10 — Unauthenticated `/search-wallet` is an app-membership existence oracle for arbitrary public keys — LOW

**Category:** exposure
**Locations:** `src/server/routes.ts:466-481`, `src/next/routes.ts:35-38`

### F11 — `/login` builds email-index and rate-limit keys from UNVALIDATED, unbounded email (storage-injection / key-bloat DoS) — LOW

**Severity:** Low (per-route validation inconsistency; storage-bloat, self-expiring)
**Category:** dos
**Locations:** `src/server/routes.ts:307-344` (esp. `:329`, `:341`), `src/server/session.ts:63-65`, `src/server/http.ts:39-45`

**Attacker + impact.** `login()` is the **only** email-bearing route that never calls `validateEmail`
(`challenge()`/`register()` both do, `routes.ts:187,235`). It takes `body.email` straight from `readJson`
(no body-size cap, `http.ts:41`) and (1) passes it to `resolvePublicKeyByEmail` → builds the `hget` key
`email:${email.toLowerCase().trim()}` (read), and (2) on credential failure builds the rate-limit identifier
`login:${appId}:${body.email}` (`routes.ts:341`) → `checkRateLimit` does `storage.incr(key)` +
`storage.expire(key,...)` — a persistent **write** keyed on attacker-controlled, unbounded, arbitrary-charset
content. Since the attacker has no valid credentials, control reliably reaches the write; varying `email` per
request mints unbounded distinct Redis/KV counter keys — the exact "attacker mints arbitrary namespaces /
storage-bloat" concern the appId validator was added for (`routes.ts:42-46`), left open on the email axis in
one route.

**Why low.** The rate-limit keys carry a 60s TTL (`config.ts:174`) so they self-expire, each request also
incurs signature-verification work, and sustained volume is bounded by the edge limiting `THREAT_MODEL` §5.3/R4
delegates; the `hget` path is read-only.

**Fix.** In `login()`, after the required-field check, call
`const emailErr = validateEmail(body.email); if (emailErr) return error(emailErr);` before
`resolvePublicKeyByEmail` and the rate-limit call — mirroring `challenge()`/`register()`. Independently, cap
request-body size in `readJson`, and truncate/hash any client-controlled component before concatenating it
into a storage key.

### F12 — `authLoginMessage` does not embed `appId` — the signed auth message is identical across all deployments — LOW

**Severity:** Low (defense-in-depth; not currently exploitable)
**Category:** auth
**Locations:** `src/core/index.ts:57-59`, `src/client/authKey.ts:24-28`, `src/server/signature.ts:65-78`

**Attacker + impact.** The message an email/biometric account signs to log in is
`Sign in to your TTC account: {challenge}` (`index.ts:58`) with **no** appId in the preimage — unlike the
wallet app-key messages and the PBKDF2 salt, which are all appId-bound. Cross-app replay is prevented **only**
by storage-layer scoping: the challenge lives under `challenge:{appId}:{publicKey}` (`keys.ts:12-14`) and is
consumed via a single atomic `getdel` + `timingSafeEqual` (`challenge.ts:34-37`), so a signature captured for
appA cannot be consumed at appB. The domain separation is real but lives in the storage key, not in the signed
bytes; the gap would become exploitable if any future change shared/reused a challenge value across appIds or
verified an auth signature outside `consumeChallenge`.

**Evidence.** `index.ts:57-59` `return \`Sign in to your TTC account: ${challenge}\`;` — contrast the
appId-bound `walletAppKeyMessage` (`index.ts:29-31`) and PBKDF2 salt `SHA-256(\`${appId}:${email}\`)`
(`crypto.ts:30`).

**Fix.** Bind the auth message to appId: `Sign in to your TTC account (App: ${appId}): ${challenge}`, threading
`config.appId` through `signAuthChallenge` and `verifyAuthSignature`, so domain separation becomes a property
of the signed bytes.

### F13 — `ExportKeyPanel` re-invokes `onReveal(plaintext)` on every parent re-render while a secret is displayed — LOW

**Severity:** Low (SDK-owned amplification footgun; no new exfil path)
**Category:** exposure
**Locations:** `src/ui/ExportKeyPanel.tsx:81-83`

**Attacker + impact.** The `onReveal` callback fires from an effect keyed on `[plaintext, onReveal]` with only
an `if (plaintext)` guard. The common inline-arrow integration (`onReveal={(k)=>...}`) changes callback
identity every render, so the effect re-runs and re-invokes `onReveal` with the **same** plaintext on every
parent re-render while the secret is on screen — not once. A consumer that innocently forwards `onReveal` into
a telemetry/log pipeline now emits the private key many times, widening the chance the key lands in a persisted
log. This is a footgun the SDK contract itself creates (not a documented/accepted trust boundary).

**Evidence.**
```ts
useEffect(() => { if (plaintext) onReveal?.(plaintext); }, [plaintext, onReveal]);
```

**Fix.** Fire `onReveal` exactly once per reveal: track the last-emitted plaintext in a ref and only call when
the value transitions to a new non-null secret (apply the same to the `onError` effect).

### F14 — Clipboard auto-wipe unconditionally clobbers the system clipboard and cannot fire while backgrounded — LOW

**Severity:** Low (correctness/UX safety; no attacker path)
**Category:** exposure
**Locations:** `src/ui/ExportKeyPanel.tsx:110-125`

**Attacker + impact.** After copy, a timer runs `navigator.clipboard.writeText("")` `clipboardClearMs` later

### F18 — `deriveAppKeyFromPasskey` default iteration argument is 100k (legacy), not the config default 600k — INFO

**Severity:** Info (latent footgun; no live bug)
**Category:** crypto
**Locations:** `src/core/crypto.ts:23-33`, `src/client/authClient.ts:121-122, 208-209, 242-243`

**Impact.** `deriveAppKeyFromPasskey`'s `iterations` parameter defaults to `100_000` (`crypto.ts:26`), the

### F19 — Ledger off-chain fallback keys entirely off the substring `0x6a81`; any error-text drift halts the cascade — INFO

**Severity:** Info (robustness/availability hardening; no attacker, no fund/key impact)
**Category:** auth
**Locations:** `src/ledger/solanaSigner.ts:85-97`, `src/ledger/transport.ts:57-93`

**Impact.** The legacy→v0 envelope fallback continues only when `msg.includes("0x6a81")` on the thrown error's
message (`solanaSigner.ts:91`) — a single **case-sensitive lowercase** substring. Ledger status words surface
as free-text `.message` strings whose format varies by transport/adapter version (the sibling
`mapLedgerDeviceError` at `transport.ts:57-93` exists precisely because Ledger errors come in coded and worded
forms). A firmware/adapter that emits the header-rejection differently (e.g. `0x6A81` uppercase, a worded
`INCORRECT_P1_P2`, or a wrapped error omitting the raw status word) would rethrow on the first candidate and
never attempt v0 — a device that would otherwise sign is refused. `0x6a81` is a defined APDU status word that
`@ledgerhq/errors` renders lowercase, so the drift is speculative, hence info.

**Fix.** Normalize the error (lowercase) and match more robustly (`/0x6a81/i` plus known worded equivalents),
mirroring the case-insensitive matching already in `mapLedgerDeviceError`; or try every candidate on any
non-user-rejection error.

### F21 — Sole runtime dependency `@noble/hashes` is pinned to an exact version `2.2.0` (no caret) — INFO

**Severity:** Info (maintenance/patch-latency note; a legitimate supply-chain choice)
**Category:** supply-chain
**Locations:** `package.json:81-83`

**Impact.** The only hard runtime dependency, the crypto primitive `@noble/hashes`, is pinned exactly to
`2.2.0` (no `^`). It is correctly a `dependency` (not a peer), kept external in the bundle (not inlined), has

avoids a mismatched second copy, correctness is unaffected.

**Fix.** Keep the exact pin (recommended for a crypto SDK) but add a CI reminder to track `@noble/hashes`
advisories and bump promptly; or use `~2.2.0` to auto-absorb patches while blocking minor drift.

**Overall assessment.** The SDK's cryptographic and session core is well-built and calibrated to its stated
threat model; the great majority of "generic-SDK" concerns are already mitigated or explicitly delegated. The
actionable risk is concentrated in the hardware-wallet path (F1, F2), where the SDK ships a public API that its
own PRD forbids until the recovery-wrap + `keyMsgVersion` persistence lands. Prioritize F1/F2; the remainder is
avoidable-lockout and defense-in-depth hardening.
