# v0.6.0 Security Audit — SQL storage backend (`SqlAuthStore`)

**Auditor:** Claude Opus 4.8 (1M context)
**Date:** 2026-07-14
**Scope:** the changes that introduce the SQL storage tier (ADR-002) plus the v0.5.1 client
wallet-selection fix, layered on the v0.5.0 `AuthStore` seam and session-token hashing.
**Method:** multi-agent focused security review — one discovery pass over the full diff and the
surrounding security model, then independent adversarial false-positive validation of every
candidate finding, filtered at ≥8/10 confidence.

> **Verdict: no HIGH or MEDIUM vulnerability meets the reporting bar** (>80% confidence, concretely
> exploitable, newly introduced by this change). Two sub-threshold observations are documented in
> §4 with defensive fixes worth taking anyway. This audit is a snapshot of the code as reviewed;
> re-audit if the SQL engine, the drivers, or the preflight change.

### The invariants a storage backend must not break

These are the security-load-bearing properties the SDK depends on the store to uphold. The audit
traced each one through the new SQL engine:

1. **Raw session tokens are never persisted** — only `SHA-256(token)` (`tokenHash`). A store read must
   not yield a replayable bearer credential.
2. **`takeChallenge` is an atomic get-and-delete** — of N concurrent callers, exactly one may observe
   the value; otherwise single-use login challenges become **replayable** (signature/auth replay).
3. **Expiry is enforced on the read path** — `getSession` / `takeChallenge` return `null` for expired
   rows *without* relying on a sweeper, because `verifySession` accepts any non-null value
   `getSession` returns. A store that returns expired rows is accepting revoked bearer tokens.
4. **No lost write on the email index** — concurrent registrations of the same email under different
   `appId`s must both survive.
5. **Tenant / account isolation** — two `appId`s never read each other's rows; two distinct
   `publicKey`s never collide (byte-exact key comparison).
6. **Errors fail closed** — propagate; never resolve to a benign default (`{allowed:true}`, `null`).

Attacker-controlled inputs that flow toward these operations: `appId` (request body/header, validated
upstream by `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`), `publicKey`, `email`, `challenge`, and the presented
token — all reach the storage layer as method arguments.

## 3. What was verified (and why it holds)

### 3.1 SQL injection — not present

`engine.ts:50-54` `sql()` rewrites `?` placeholders to the dialect's positional form on the **statement
template only**:

```ts
private sql(parts: TemplateStringsArray | string): string {
  const raw = typeof parts === "string" ? parts : parts.join("");
  let i = 0;
  return raw.replace(/\?/g, () => this.dialect.placeholder(i++));
}
```

Every `this.run(...)` call was traced. The template is built exclusively from **string literals +
dialect-controlled table names + dialect fragments** (`upsert()`, `forUpdate`). No attacker input is
ever interpolated — `appId`, `publicKey`, `email`, `challenge`, `tokenHash`, `identifier` all arrive
in the `params` array and are bound by the driver. Because values never pass through `sql()`, a `?`
inside a *value* cannot shift placeholder numbering; and no dialect fragment contains a stray `?` that
would desync Postgres `$N` numbering. The `tests/sql-dialects.test.ts` invariant *"no parameter value
is EVER interpolated into the SQL text"* independently asserts this across all three dialects.

### 3.2 Placeholder / parameter binding — correct

Hand-counted placeholders vs. `params.length` for the multi-value statements, including the
double-bind pattern (a value passed twice so the same literal serves both the INSERT and the
ON-CONFLICT UPDATE under positional `$N`):

- `putUser` — users upsert 4/4, email-index upsert 4/4 ✓
- `putChallenge` — 6/6 ✓
- `putSession` — 8/8 ✓
- `hitRateLimit` — 7/7, including the two CASE `expires_at <= ?` binds ✓

Ordering matches column order in every case.

### 3.3 Challenge replay — prevented per dialect

`takeChallenge` is atomic on every engine, and filters expiry:

- **Postgres / SQLite:** single-statement `DELETE … WHERE app_id = ? AND public_key = ? AND expires_at
  > ? RETURNING challenge` — exactly one concurrent caller wins.
- **MySQL** (no `DELETE … RETURNING`): `SELECT … FOR UPDATE` then `DELETE`, inside a transaction on a
  checked-out connection. `mysqlDriver.transaction` **throws** if handed a client that cannot check
  out a connection (`drivers.ts`), so the locking guarantee cannot silently degrade to a pool-scattered
  non-transaction.

### 3.4 Expired-session acceptance — prevented

Every expiry-bearing read filters `expires_at > ?`: `getSession`, `takeChallenge`, and (MySQL) the
rate-limit count is read back *after* the CASE that resets an expired window. `sweepExpired` uses
`<=` and is space-reclamation only. `deleteSession` is the sole unconditional statement and is a
revoke. Confirmed by the dialect test *"every expiry-bearing READ filters on expires_at"*.

### 3.5 Fail-closed error handling — upheld

- `engine.ts` `getUser` catches only `JSON.parse` of an already-returned row (matching `KvAuthStore`);
  it never wraps the query, so a DB error propagates.
- `index.ts` `createSqlAuthStore` runs `preflight` with **no** surrounding try/catch — a throwing
  preflight rejects construction. `skipPreflight` defaults falsy.
- `dialects/postgres.ts` preflight wraps **only** the WARN-level nondeterministic-collation diagnostic
  in try/catch; the boot-refusing `public_schema` and `missing_tables` checks sit outside it, so
  swallowing a diagnostic query error cannot convert an error-level condition into a pass.

### 3.6 Tenant / account isolation — enforced

Every statement is keyed on `(app_id, …)`; primary keys are `(app_id, public_key)`,
`(app_id, token_hash)`, `(email, app_id)`, `(endpoint, app_id, identifier)`. Byte-exact comparison is
enforced per engine — Postgres deterministic collation, SQLite `BINARY`, MySQL `VARBINARY` (plus the
driver's Buffer→UTF-8 decode, §3.8). `getPublicKeyByEmail` is app-scoped. The conformance suite's
`Acme`/`acme` tenant test and `K`/`k` public-key test pass on all three real engines.

### 3.7 Token-at-rest — digests only

Only `hashSessionToken()` (SHA-256 hex, `core/crypto.ts`) reaches storage; `token_hash` columns are so
named and documented. `session.ts` confirms the raw token is never written to the record either
(the v0.5.0 fix). A dumped SQL table therefore yields digests, not replayable credentials.

### 3.8 Driver-level concerns — reviewed clean

- `mysqlDriver.decode()` (`drivers.ts`) converts `Uint8Array` (mysql2 returns `VARBINARY` as `Buffer`)
  to a UTF-8 string on the **read path only**; it never builds SQL. Without it, key comparisons would
  silently fail — a correctness fix, no injection or type-confusion surface. `count` (BIGINT) is
  coerced with `Number(...)`.
- Nested `transaction: (inner) => inner(tx)` (pg/mysql) and the SQLite `depth > 0 → fn(driver)`
  short-circuit are only reachable if the **engine** nests transactions. It does not: `putUser`, and
  MySQL's `takeChallenge` / `hitRateLimit`, each open exactly one transaction and issue only
  non-transactional statements within. Atomicity intact.
- `deleteExpiredLimited`'s `limit` is coerced `Math.max(1, limit | 0)` and originates from the
  integrator's `sweepExpired()` cron, not any attacker-reachable route.

### 3.9 Client wallet changes — a security improvement, not a regression

`authClient.ts` `web3WalletGen` strips the redundant Solana `funds` role for Web3 logins, and
`useActiveWallet` / `useWallets` now resolve the Solana identity from `user.publicKey` (the record)
rather than the nullable `externalSolanaAddress` prop, marking external keys `encrypted: null`. Net
effect: the SDK no longer mints or holds an unrequested key for a Web3 user, and the UI can no longer
surface a wrong (stray-embedded) deposit address. Email/biometric paths are unchanged. No
key-exposure regression. (Background: this is the v0.5.1 fix for the reported "funding wallet /
private key shown after Web3 login" defect.)

## 4. Sub-threshold observations (filtered out — recommended fixes anyway)

Both were independently validated by an adversarial sub-task and scored **2/10** against the review's
false-positive rules. Neither is a reportable vulnerability; both are cheap hardening.

### 4.1 SQLite driver `try{all}catch{run}` — a rate-limit fail-open under a transient error

`src/storage/sql/drivers.ts:178-183`

```ts
try {
  return stmt.all(...params) as T[];
} catch {
  const info = stmt.run(...params);
  return [{ affected: info.changes }] as unknown as T[];
}
```

**Why it is NOT a reportable vuln.** In `better-sqlite3`, reader vs. non-reader is fixed at *prepare*
time; `.all()` on a non-reader throws a **type guard before executing** (`This statement does not
return data`). So for the write paths (`putSession`, `putUser`, `putChallenge`, `deleteSession` — all
non-RETURNING) the catch's `.run()` is the first and only execution, and a genuine `SQLITE_CONSTRAINT`
/ disk / lock error surfaces from `.run()` and **propagates (fail closed)**. The catch can only swallow
a *mid-execution* error for a RETURNING statement whose `.all()` throws and whose `.run()` retry then
succeeds — reachable only by the rate-limit upsert (whose fail-open reads `rows[0]?.count ?? 1` →
`{allowed:true}` at `engine.ts:267`). That requires a transient `SQLITE_BUSY` that clears in the
microseconds between two synchronous calls, on a backend documented as single-process dev/self-host
only. No attacker can induce it, and rate-limiting is an explicit review exclusion.

**Recommended fix (defensive):** don't catch-all. Branch on `dialect.supportsReturning`, or narrow the
catch to the specific *"does not return data"* `TypeError`, so a real execution error can never be
converted into a synthetic success row.

```ts
async query<T>(sql, params) {
  const stmt = db.prepare(sql);
  if (stmt.reader) return stmt.all(...params) as T[];   // better-sqlite3 exposes `.reader`
  const info = stmt.run(...params);
  return [{ affected: info.changes }] as unknown as T[];
}
```

### 4.2 `web_served_path` preflight guard misses leading-slash-less relative paths

`src/storage/sql/dialects/sqlite.ts:24, 116-117`

```ts
const WEB_SERVED = ["/public/", "/static/", "/www/", "/dist/", "/.next/static/"];
// …
const normalized = opts.path.replace(/\\/g, "/");
if (WEB_SERVED.some((d) => normalized.includes(d))) { /* refuse to boot */ }
```

The substring match requires leading and trailing slashes, so the *most common* Next.js layout —
`path: "public/auth.db"` (relative to cwd) — and nested dirs like `public/data/…` slip through.

**Why it is NOT a reportable vuln.** `opts.path` is trusted integrator configuration, not attacker
input (config values are trusted per the review's precedents). The SDK never serves the file; exposure
additionally requires the integrator to place the DB under a served directory *and* the framework to
serve it. This is an **imperfect newly-added defense-in-depth check**, and the underlying risk is
"secrets stored on disk" — both review exclusions. Bypassing an advisory boot warning is not itself an
exploit.

**Recommended fix (defensive):** resolve the path (`path.resolve`) and match on **path segments**, not
raw substrings, so relative and nested placements are caught:

```ts
const segments = new Set(resolve(opts.path).split(sep));
if (["public", "static", "www", "dist"].some((d) => segments.has(d))) { /* … */ }
```

## 5. Positive security notes

Worth recording, because they are the reason the finding count is zero:

- **The SDK owns the correctness, not the integrator (ADR-002).** Every hazard that used to be a
  per-backend security exam — expiry-on-read, atomic consume, the rate-limit window, no-lost-write,
  email normalization, collation, key sizing, injection — is implemented once in `SqlAuthStore` and
  the generated DDL. A dialect author supplies ~30 lines with no auth logic, and so cannot introduce
  these classes of bug.
- **Preflight fails the deploy, not the users.** The genuinely dangerous, *silent* misconfigurations
  are boot-refusing errors, not documentation: Supabase's world-readable `public` schema, MySQL not in
  strict mode (silent truncation → wallet lockout), non-binary MySQL key columns, missing tables.
- **Parameterization is structurally guaranteed** by the `sql()` template design and asserted by a
  dedicated per-dialect test rather than left to reviewer diligence.
- **Verified against real engines, not mocks.** The full 24-case conformance suite runs against real
  Postgres, MySQL, and SQLite (SQLite in-process on every test run; Postgres/MySQL/Redis in CI). This
  is what surfaced the two bugs fixed *before* this audit — a `;`-in-DDL-comment schema split and
  mysql2's `VARBINARY→Buffer` return type — neither of which a mock or a single engine would have
  shown.

## 6. Methodology

1. **Discovery** — one agent read the full diff and the surrounding security model, tracing each
   attacker-controlled input into SQL construction and into every read, against the six invariants in
   §1.3.
2. **Adversarial validation** — each candidate was handed to an independent agent instructed to *break*
   it (confirm the `better-sqlite3` execution semantics, the path-match behavior) and score true-positive
   confidence 1–10 under the false-positive-filtering rules (DoS / rate-limiting / secrets-on-disk /
   config-is-trusted exclusions).
3. **Cutoff** — report only ≥8/10. Both candidates scored 2/10 and were filtered.

**Explicit exclusions honored** (not reviewed as vulnerabilities): denial of service / resource
exhaustion, rate-limiting-only concerns, secrets stored on disk, third-party dependency versions,
theoretical timing/races, and findings confined to test or documentation files.

| # | Item | Priority |
|---|---|---|
| 1 | §4.1 — narrow the SQLite driver catch (branch on `supportsReturning` or `stmt.reader`) so a real execution error can never become a synthetic success. | Low (defensive) |
| 2 | §4.2 — resolve + segment-match the `web_served_path` guard so relative/nested placements are caught. | Low (defensive) |
| 3 | Keep the real-engine conformance runs (Postgres + MySQL) **required** in CI. They are what makes the "same engine, any database" guarantee true rather than asserted. | Maintain |

Neither §4 item blocks release. The SQL storage tier is, from a security standpoint, ready to ship.
