# v0.5.0 — Storage foundation: harden what Redis already stores, and make the seam contractual

**Ship no new database providers. Fix the seam they will plug into.** `0.5.0` stays Redis-only
(Redis / Upstash / Vercel KV / Memory, exactly as today) and does the work that must land *before* a
second backend exists — because every item here is either (a) a security fix that is cheap now and
expensive once third-party adapters are in the wild, or (b) an **interface commitment** that gets
frozen the moment someone implements it outside this repo.

- **Status:** ✅ **IMPLEMENTED AND SHIPPED (`0.5.0`).** All five workstreams landed, and the last
  open item — the **real-Redis conformance run** (§3.4) — is now closed: the suite runs against a
  live `redis:7-alpine` service in CI and **all 22 cases pass**. `tsc --noEmit` clean, Prettier
  clean, full Jest suite green, `npm run build` emits the `@tetrac/login-sdk/storage/conformance`
  subpath.

  > **What the real-Redis run actually proved.** `MemoryAdapter` is the normative reference
  > implementation every future backend is written to match, but *"matches Redis"* had never been
  > executed — it was an assertion in a code comment. The engine-level invariants it rests on
  > (`INCR` on an **expired** key returns `1` and drops the stale TTL; `INCR` on a **live** key
  > preserves its TTL; `GETDEL` is atomic under concurrency; an expired key is invisible on every
  > read path) now hold **on the real engine**, exactly as modelled. If the reference implementation
  > had been wrong, every adapter built on it would have inherited the same wrong model.
- **Scope:** Redis family only. **No** Postgres, SQLite, Mongo, MySQL, or Convex backend ships here —
  that is [`docs/MULTI_DB.md`](../docs/MULTI_DB.md), retargeted at `0.6.0`.
- **Why now, in one line:** the two things that must be right *before* a second backend exists are
  **what we store** (raw session bearer tokens — §1) and **the shape of the port** (`StorageAdapter`
  is Redis-shaped, and it forbids correct implementations on other engines — §3). Both are true on
  Redis today. The multi-DB work made them visible; it did not create them.
- **Driver:** Security + architecture. §1 and §2 are user-visible improvements to the **current**
  Redis deployment. §3 is the migration runway, and it is the reason this release exists.
- **Breaking:** one type change (`UserData.authToken`), an **internal** refactor of the server's
  storage calls, and **one forced re-login for every user** (§6). The public API and the client are
  untouched. No data migration, no backfill.

## 1. Hash the session token at rest 🚨

### 1.1 The problem is bigger than the session key

Today the raw session bearer token is written to storage in **two** places, and both must change
together or the fix is theatre:

1. **The session key itself** — `session:{appId}:{token}` → `publicKey`
   ([`session.ts:129-131`](../src/server/session.ts#L129-L131)).
2. **Inside the `UserData` blob** — `issueSession` does `user.authToken = token` and persists the
   record ([`session.ts:90-91`](../src/server/session.ts#L90-L91)), so the same raw token is also
   sitting in the `pubKey:{appId}:{publicKey}` value, as a plain JSON field
   ([`types.ts:68`](../src/core/types.ts#L68)).

> **This is the correction that makes this workstream worth its own section.** The multi-DB review
> proposed hashing the session *key* only. That alone would have been a **false fix**: the raw
> token would still be readable in every `UserData` blob, so a world-readable table (or a backup,
> or a replica) would still hand an attacker a live, replayable credential for every user who has
> logged in. Hashing one of the two locations achieves nothing.

Anyone who can read the store — a leaked backup, a read replica, an analytics sync, another
service sharing the DSN, a `SELECT` from unrelated app code, or (in `0.6.0`) a misconfigured
Supabase `public` schema — can **replay these tokens directly**. No cracking step, no escalation.
That posture was defensible when the store was a private, ephemeral, in-memory Redis that nobody's
BI tool pointed at. It is not defensible for the backends `0.6.0` invites, and it is not actually
great now.

### 1.2 The fix

The token is `randomHex(32)` — **256 bits of CSPRNG entropy**
([`crypto.ts:109-111`](../src/core/crypto.ts#L109-L111)). That is the fact that makes this easy:
there is no dictionary to attack and no precomputation that beats a uniform 2²⁵⁶ space, so it
needs **no KDF, no salt, no stretching**. A plain SHA-256 is a preimage-resistant index over it —
the same construction GitHub uses for personal access tokens and every well-built API-key store
uses for keys. (Do **not** reach for PBKDF2 here out of caution: it would add ~600ms to *every
authenticated request* and buy exactly nothing.)

```ts
// src/core/crypto.ts — beside the existing hashUserAgent(), same primitives already imported
/** SHA-256 (hex) of a session token. The token is 256 bits of CSPRNG output, so a bare
 *  hash is sufficient — there is no dictionary to stretch against. The RAW token is a
 *  bearer credential held only by the client; storage only ever sees this digest. */
export function hashSessionToken(token: string): string {
  return bytesToHex(sha256(utf8ToBytes(token)));
}
```

```ts
// src/core/types.ts — UserData
- authToken: string;              // the raw bearer token. Removed.
+ /** SHA-256 of the user's current session token. Never the token itself — the raw token
+  *  exists only in the client's hands. Used to revoke the previous session on re-login. */
+ authTokenHash?: string;
```

```ts
// src/server/session.ts
function sessionKeyFromHash(appId: string, tokenHash: string, config: AuthConfig): string {
  return appScoped(config.keyPrefixes.session, appId, tokenHash);
}
/** Raw token in, storage key out. The ONLY place a raw token is hashed on the read path. */
function sessionKey(appId: string, token: string, config: AuthConfig): string {
  return sessionKeyFromHash(appId, hashSessionToken(token), config);
}

export async function issueSession(storage, user, config, fingerprint?): Promise<string> {
  // Revoke the previous session by its stored HASH — we no longer hold its raw token,
  // and we don't need to: the hash IS the key.
  if (user.authTokenHash) {
    await storage.del(sessionKeyFromHash(user.appId, user.authTokenHash, config));
  }
  const token = generateSessionToken();
  const tokenHash = hashSessionToken(token);
  await storage.set(
    sessionKeyFromHash(user.appId, tokenHash, config),
    encodeSessionValue(user.publicKey, fingerprint),
    { exSeconds: config.sessionTtlSeconds },
  );
  user.authTokenHash = tokenHash;
  delete (user as { authToken?: string }).authToken;   // scrub any legacy raw token on write (§6)
  await persistUser(storage, user, config);
  return token;                                        // raw token goes to the CLIENT and nowhere else
}
```

`verifySession` and `revokeSession` both already funnel through `sessionKey()`, which now hashes
internally — **so neither changes at all**, and the `/logout` route keeps passing the raw header
token straight through ([`routes.ts:451`](../src/server/routes.ts#L451)). The lookup stays O(1); it
is still a single point-read, just on a digest.

**The one place that does need surgery is how the token reaches the response.** Today
`issueSession` mutates `user.authToken` and `asResult(user)` reads it back off the object
([`routes.ts:151-152`](../src/server/routes.ts#L151-L152)) — a side-channel that only worked
because the raw token was persisted. It must become an explicit argument:

```ts
- function asResult(user: UserData): AuthResult {
-   return { publicKey: user.publicKey, authToken: String(user.authToken), user: publicUser(user) };
+ function asResult(user: UserData, token: string): AuthResult {
+   return { publicKey: user.publicKey, authToken: token, user: publicUser(user) };
  }

// at all four call sites (routes.ts:303, 338, 374, 438):
- await issueSession(storage, user, config, issueFingerprint(req));
- return json(asResult(user));
+ const token = await issueSession(storage, user, config, issueFingerprint(req));
+ return json(asResult(user, token));
```

`publicUser()` currently strips `authToken` ([`routes.ts:147`](../src/server/routes.ts#L147)); it
must strip **`authTokenHash`** instead. The digest is not a credential, but it is a session
identifier and the client has no use for it.

**`AuthResult.authToken` does not change.** The client still receives the raw token, still stores
it in `localStorage`, still sends it in the `ttc-auth-token` header. **The entire client contract
is untouched** — `authClient.ts` and `client/session.ts` need zero changes. This is a server-side
storage change only.

### 1.3 What it buys

A full read of the storage layer now yields: encrypted wallet blobs (already ciphertext, already
behind 600k PBKDF2 iterations) and a column of **64-hex digests that cannot be replayed**. The
attacker learns *that* a session exists and which `publicKey` owns it. **They cannot become that
user.**

That is the difference between a metadata leak and total account takeover, and it holds for every
leak channel at once — backups, replicas, logs, the `0.6.0` Supabase exposure — rather than
plugging them one at a time. It is the single highest-leverage change in this release and the
reason the release exists.

> **Not touching the challenge key.** `challenge:{appId}:{publicKey}` → challenge: there the
> *value* is the secret and the key is not, so hashing the key buys nothing. The challenge value is
> single-use, 5-minute TTL, and worthless without the wallet's private key. Leave it. This section
> is about the session token specifically, because it is the only stored value that is directly
> replayable as a credential.

## 2. `close?()` and `sweepExpired?()` — optional, and useful today

Both are added to `StorageAdapter` as **optional** methods, so every existing adapter — and every
adapter anyone has already written — stays structurally valid. Callers **must** feature-detect.

```ts
// src/storage/adapter.ts
export interface StorageAdapter {
  /* …the 10 required methods, signatures unchanged… */

  /**
   * OPTIONAL. Release pooled connections / handles. Idempotent — calling it twice is safe,
   * and calling it on an adapter that never opened anything is a no-op.
   * Adapters over a stateless REST client (Upstash, Vercel KV) or an in-process Map omit it.
   * Callers feature-detect: `await storage.close?.()`.
   */
  close?(): Promise<void>;

  /**
   * OPTIONAL. Delete expired entries; returns how many were removed. `limit` bounds one batch.
   *
   * SPACE RECLAMATION ONLY. This is NEVER the expiry authority: every adapter must already
   * make an expired entry invisible on the READ path, whether or not this has ever run. An
   * adapter that relies on a sweep for correctness is non-conformant (see STORAGE_ADAPTERS.md).
   * Adapters with native expiry (Redis, Upstash, Vercel KV) omit it.
   */
  sweepExpired?(limit?: number): Promise<number>;
}
```

**Why ship them in a release with no backend that needs them?** Because the framing "groundwork" is
only half true — each one fixes something real today:

- **`close()` on `RedisAdapter`.** `ioredis` holds a live socket. A long-lived Node/Express server,
  a test suite, or a script that calls `resolveStorageAdapter()` has **no way to release it today**
  — Jest hangs on open handles, and graceful shutdown leaks a connection per reload. Implement as
  `await this.client.quit?.()`, with `quit?(): Promise<unknown>` added to `RedisLike` as an
  **optional** member so existing mocks still satisfy the type. Upstash/Vercel KV omit it (HTTP,
  nothing to close).
- **`sweepExpired()` on `MemoryAdapter`.** `MemoryAdapter` expires **lazily** — `alive()` only
  deletes an entry when something reads it ([`memory.ts:17-25`](../src/storage/memory.ts#L17-L25)).
  Rate-limit counters, abandoned challenges, and expired sessions are typically **never read
  again**, so a long-running process (a dev server, a soak test) grows monotonically. This is a
  real leak, it exists now, and `sweepExpired()` is its fix. `MemoryAdapter` is also the
  **normative reference implementation**, so its sweep is the one every future SQL adapter is
  written against.

And the strategic reason, which is the one that actually forces the timing: **these are public,
third-party-implementable interfaces.** Adding a method after external implementations exist is a
breaking change *to them*. Adding it while we are the only implementer costs nothing. If these
methods are ever going to exist, they exist now.

> **Both methods land on `AuthStore` as well** (§3) — that is the port third parties actually
> implement. `KvAuthStore` delegates to the underlying `StorageAdapter`'s versions when present, and
> omits them when not. They stay optional on both interfaces.

No caller in the SDK invokes either method in the request path. `close()` is for the app's shutdown
hook; `sweepExpired()` is for `0.6.0`'s reaper wiring. Both are documented, both are tested, and
`0.5.0` ships them unused-but-correct — which is exactly what an interface commitment is.

## 3. 🚨 The `AuthStore` seam — and a conformance suite against the *right* interface

Full reasoning: **[`ADR-001`](./ADR-001-storage-seam.md)** (accepted). The summary, because it
reshapes this release:

### 3.1 Why the current port is wrong

`StorageAdapter` is named for what it **is** (a key-value store) rather than for what it is **for**
(authentication state). That inverts the dependency: every backend must **emulate Redis** instead of
doing what it is good at — and we compensated by writing eleven pages of hazards explaining how to
emulate Redis *correctly*.

Convex is the proof. Its own error documentation uses **our exact data structure** as its worked
example of an anti-pattern: a mutation that *"always updates the same document"* under
optimistic concurrency control will, *"if the mutation is called more rapidly than Convex can
execute it,"* **throw a write-conflict error**. Their example code is `patch(doc, {value: value+1})`
— that is `INCR` on a hot key. A rate-limit counter is, by definition, many writes to one document.
So `incr()` on Convex **fails hardest under precisely the burst traffic a rate limiter exists to
survive.**

Convex's own fix is a **sharded** counter (their `@convex-dev/rate-limiter` does exactly this, and
*"fails closed, not open"*). **We cannot use it**, because `StorageAdapter.incr(key)` is a
*primitive*, not a *decision* — it hands the backend a mechanism and denies it the intent. Sharding
is trivial for a backend asked `hitRateLimit(...)` and **impossible** for one asked `INCR`.
**The port forbids the only correct implementation.**

And this is not a Convex quirk. Auditing `docs/MULTI_DB.md` §3 against a domain-shaped port:
**six of its eleven correctness hazards are artifacts of the KV seam, not of the problem** —
§3.1 (the permanent-lockout bug — becomes *unrepresentable*), §3.5 (collation), §3.6 (key sizing),
§3.8 (`del` across keyspaces), §3.9 (key-length bounds), and half of §3.4. They exist only because
we serialize domain identities into opaque strings and emulate Redis commands. **They are our own
hazards.**

### 3.2 The port (which already exists — it just isn't an interface)

Every storage access in the server already funnels through nine functions in `session.ts`,
`challenge.ts`, and `rateLimit.ts`; `routes.ts` never touches `storage` directly. **The domain layer
is written.** We are promoting it to an interface, not designing one.

```ts
// src/storage/store.ts
export interface AuthStore {
  // users
  getUser(appId: string, publicKey: string): Promise<UserData | null>;
  putUser(user: UserData): Promise<void>;                 // upsert + maintain the email index
  getPublicKeyByEmail(appId: string, email: string): Promise<string | null>;

  // challenges — single-use, TTL-bound
  putChallenge(appId: string, publicKey: string, challenge: string, ttlSeconds: number): Promise<void>;
  /** ATOMIC. Returns the stored challenge and removes it. null if absent OR expired.
   *  The caller does the constant-time compare — never the backend. */
  takeChallenge(appId: string, publicKey: string): Promise<string | null>;

  // sessions — keyed by the token's SHA-256 digest, never the token (§1)
  putSession(appId: string, tokenHash: string, s: SessionValue, ttlSeconds: number): Promise<void>;
  getSession(appId: string, tokenHash: string): Promise<SessionValue | null>;   // null if expired
  deleteSession(appId: string, tokenHash: string): Promise<void>;

  // rate limiting — ONE atomic call returning a DECISION, not a counter.
  // The bucket is STRUCTURED, not a concatenated string: that is what lets a backend
  // index it, and shard it.
  hitRateLimit(
    bucket: { endpoint: string; appId: string; identifier: string },
    windowSeconds: number,
    maxAttempts: number,
  ): Promise<RateLimitResult>;

  // lifecycle — optional, feature-detected (§2)
  sweepExpired?(limit?: number): Promise<number>;
  close?(): Promise<void>;
}
```

Eleven methods against the KV port's ten — **no bigger, and every one is easier to implement
correctly**, because you write the query your database is actually good at. Two wins fall out for
free: `SessionValue` is `{ publicKey, fingerprint? }`, which **deletes the `publicKey|fingerprint`
string-splitting hack** in `session.ts` (whose correctness currently rests on "wallet public keys
never contain `|`"); and `putUser` can write the record **and** the email index in **one
transaction** on any real backend, where today it is two non-atomic calls.

### 3.3 Nothing breaks — `StorageAdapter` becomes a *KV-backend* contract

- **`KvAuthStore` implements `AuthStore` over any `StorageAdapter`.** Its body is essentially
  today's `session.ts` / `challenge.ts` / `rateLimit.ts`, moved behind the interface.
- **`RedisAdapter`, `UpstashAdapter`, `VercelKVAdapter`, `MemoryAdapter`: zero changes.**
- **`createNextAuthRoutes({ storage })` keeps working** — a `StorageAdapter` is auto-wrapped in
  `KvAuthStore`. A new `{ store }` option accepts a native `AuthStore`. Purely additive.
- The refactor is internal: `session.ts`/`challenge.ts`/`rateLimit.ts` take `store: AuthStore`
  instead of `storage: StorageAdapter`. Mechanical, but it touches every route.

### 3.4 The conformance suite — one suite, on `AuthStore`

`src/storage/conformance.ts`, exported at `@tetrac/login-sdk/storage/conformance` (own subpath, so
it never lands in a server bundle). **Framework-agnostic** — it returns cases rather than calling
`describe`/`it`, so third-party authors can run it under Jest, Vitest, or `node:test`:

```ts
export interface ConformanceCase { name: string; run(): Promise<void>; }   // throws on failure
export function authStoreConformanceCases(
  makeStore: () => AuthStore | Promise<AuthStore>,
  opts?: { advance?: (ms: number) => Promise<void> | void; supportsSweep?: boolean },
): ConformanceCase[];
```

**KV backends are tested *through* `KvAuthStore`** — so one suite covers everything, and the existing
KV-primitive tests survive as unit tests of `KvAuthStore` itself. The cases now assert **observable
auth behavior** rather than Redis-primitive semantics, which is why they transfer to a backend that
has no `INCR` at all:

| Case | Guards |
|---|---|
| after a window elapses, a previously-limited identifier is allowed again | 🚨 **the permanent rate-limit lockout** (MULTI_DB §3.1) — now a *behavioral* assertion, so it holds for a sharded or lazily-recomputed backend too |
| a live window's limit is not silently extended by further hits | window drift |
| N concurrent `takeChallenge` — **exactly one** caller observes the value | 🚨 **challenge replay** |
| `takeChallenge` returns null for an expired challenge, with **no sweep having run** | expiry-on-read (MULTI_DB §3.2) |
| `getSession` returns null past the TTL, with **no sweep having run** | 🚨 **expired sessions accepted** |
| concurrent `putUser` for the same email under two different `appId`s — **neither write is lost** | lost registration (MULTI_DB §3.4) |
| a tenant whose `appId` contains a dot (`"myapp.example"`) is isolated from one named `"myapp"` | cross-tenant collision — the `appId` regex permits `.`, and it is the *recommended* format |
| `appId` `"Acme"` and `"acme"` are independent tenants; `publicKey` `"K"` and `"k"` are independent users | case-collation collision |
| a 64-wallet `UserData` round-trips **byte-identical** | silent truncation ⇒ permanent wallet lockout |
| injection-shaped values (`' OR 1=1 --`, `{"$gt":""}`, `{"$ne":null}`) round-trip as inert data | SQL / NoSQL injection |
| *(if `supportsSweep`)* `sweepExpired()` removes only expired entries, respects `limit`, returns a count | §2 |

**Fail-closed (MULTI_DB §3.10) is deliberately NOT a conformance case.** It cannot be: asserting
that a store propagates errors requires *injecting* a fault, which you cannot do to an arbitrary
conforming store handed to you as a black box. It is instead a **server-side** test — a
`BrokenRateLimitStore` whose `hitRateLimit` throws, asserting the route rejects rather than
allowing (§4.3). Saying so explicitly, because "it's covered by conformance" would be a comfortable
and false assumption.

Each case **must be written failing-first** against a deliberately-naive store, or it is not pulling
its weight — and that is itself enforced: `tests/storage-conformance-negative.test.ts` implements the
store a competent engineer plausibly writes on the first try (counter with no window, get-then-delete
challenge, expiry left to "the reaper", read-modify-write email index, case-folded keys) and asserts
the suite **catches all seven** critical bugs. A suite that cannot fail is decoration.

**Run against:** `MemoryAdapter`, `RedisAdapter`, `UpstashAdapter`, `VercelKVAdapter` (all via
`KvAuthStore`; the existing mocks fold in as the regression baseline) — **plus a dockerized real
`redis:7-alpine` in CI.**

> **The real-Redis run is the point.** `MemoryAdapter` is the normative reference implementation and
> every future backend will be written to match it — but *"matches Redis"* is currently an assertion
> in a code comment that has **never been executed**. Expiry semantics, `INCR` on an expired key, and
> `GETDEL` atomicity are properties of the **engine**; a mock only asserts we mocked it the way we
> imagined. Running the suite against a real Redis now converts `MemoryAdapter`'s normative status
> from a claim into a tested fact — *before* anything is built on top of it. If the reference
> implementation is wrong, this is the cheap release to find out. Discovering it in `0.6.0` means
> three adapters are wrong too.

## 4. Three prerequisite fixes

Small, independent, mergeable on their own — and each one is load-bearing for something `0.6.0`
wants to claim.

**4.1 `MemoryAdapter.del` must also clear the hash keyspace.** Redis `DEL` removes a key of any
type; `RedisAdapter` inherits that. `MemoryAdapter.del` deletes only from `store`, never `hstore`
([`memory.ts:38-40`](../src/storage/memory.ts#L38-L40)). **These already disagree**, silently. It is
unobservable today (no caller `del`s an email-index key) and it is a one-line fix — but the
divergence means the "normative reference implementation" is currently *not* normative, which
undercuts §3. Fix it, and let the new conformance case be the thing that would have caught it.

**4.2 `/login` must validate `body.email` before it becomes a storage key.** `POST /login` checks
only that `body.email` is *present*, then feeds it straight into two storage keys — the email index
(`email:{address}`) and a rate-limit counter — with **no `validateEmail` call**
([`routes.ts:313-341`](../src/server/routes.ts#L313-L341)). `/register` validates first
([`routes.ts:234-252`](../src/server/routes.ts#L234-L252)). So an unauthenticated caller can submit
a **1 MB `email`** and have it become a Redis key.

On Redis this is inert — keys are effectively unbounded and the lookup simply misses. It is **not**
an auth bypass on any backend: `/login` still requires a valid ed25519 signature over a consumed
challenge. But `0.6.0` sizes its key column at 512 bytes by deriving a worst case from the
validators, and **that derivation is unsound while this path exists** (on Postgres a 1 MB key is an
unauthenticated 500; on non-strict MySQL it is a silent key truncation). Three lines, and it makes
`/login` consistent with `/register` — it rejects only inputs that are already outside the
documented format.

**4.3 A fail-closed regression test.** `checkRateLimit` has no `try`/`catch`: if `incr` throws, the
exception propagates and the request 500s. That is **correct** — a rate limiter that cannot count
must not grant permission. It is also **currently untested**, and it is exactly the invariant a
future pooled-SQL adapter author will be tempted to "fix" with a `catch` that returns `0`, silently
disabling rate limiting under precisely the load that caused the failure. Add a fault-injecting fake
adapter whose `incr` rejects, and assert the route fails closed. This pins the behavior before
anyone has a reason to break it.

## 5. Docs + the `multi-database` skill

- **`docs/STORAGE_ADAPTERS.md` (new)** — the contract from §3, written *for adapter authors*: the
  expiry invariants, the atomicity requirements, the opaque-key rule, the optional methods, and how
  to run the conformance suite against your own adapter. This is the artifact `0.6.0` and every
  community adapter are built against.
- **`src/storage/adapter.ts`** — the invariants go into the interface's doc comments, not just the
  markdown. The contract should be readable at the point of implementation.
- **`docs/THREAT_MODEL.md`** — item 6 currently reads *"Production storage: a persistent KV/Redis
  (not the in-memory adapter), and TLS everywhere"* ([line 85](../docs/THREAT_MODEL.md)). It needs:
  (a) session tokens are now **stored as digests**, so read access to the store is no longer
  equivalent to account takeover — this is a genuine improvement to the model and should be stated
  as one; (b) a first-class row for **storage-layer misconfiguration** as a trust-boundary failure,
  which the model currently has no line for; (c) the standing note that the store still holds
  encrypted wallet blobs, i.e. an offline-cracking corpus, which hashing does *not* address.
- **`docs/MULTI_DB.md`** — retarget to `0.6.0`; mark §3.8, §3.9, §3.10, §4.6 as **landed in
  `0.5.0`** and strike them from its scope.
- **`README.md`** — the storage section, and a note that `close()` now exists for long-lived servers.
- **Mark `VercelKVAdapter` as legacy** (README + `STORAGE_ADAPTERS.md`). **Vercel sunset Vercel KV in
  Oct 2024**; it is now a Marketplace redirect to Upstash, and its npm package sits at ~316K
  weekly downloads against Upstash's 3.2M (§9.2). The adapter keeps working and costs nothing to
  keep (it shares `KvLike` with Upstash) — but the docs should stop presenting a dead product as a
  headline backend, and should point new deployments at Upstash. Add a comment in `resolve.ts`
  noting that its existing Upstash-before-Vercel-KV precedence is now **deliberate**, not incidental.
- **`.claude/skills/multi-database/SKILL.md`** — currently a 0-byte stub. It should teach an agent
  to (a) implement a new `StorageAdapter` against the contract, (b) run the conformance suite, and
  (c) recognize the specific hazards that make a *plausible* adapter *wrong* — the expired-`incr`
  lockout, read-path expiry, per-field hash atomicity, binary/non-padding collation, key sizing,
  injection safety. The failure mode this skill exists to prevent: an adapter that passes a smoke
  test and permanently locks users out a week later.

## 6. Breaking changes & migration

Two, and only two. Both are worth stating in the release notes **above** the feature list.

**6.1 Every user is logged out once.** Existing session keys are keyed by the raw token; after the
upgrade the server looks up `session:{appId}:{SHA-256(token)}`, which does not exist. Every live
session is therefore dead on deploy.

- **Self-healing.** Users re-login; the session TTL is 4h and each login already revokes the prior
  token, so nothing lingers. The stale raw-token keys expire on their own within one TTL.
- **No data migration, no backfill, no dual-read window.** A dual-read fallback is *possible* — but
  it would keep raw tokens readable and accepted for the length of that window, which is the exact
  thing this release exists to stop. Not worth it for one re-login.
- This is the whole cost of §1, and it is why §1 should ship **now** rather than after the SQL
  adapters: doing it later means paying this same cost later, on a larger user base, with the
  vulnerable window left open in between.

**6.2 `UserData.authToken` → `UserData.authTokenHash`.** *(Softer than expected — corrected during
implementation.)* `UserData` never **declared** an `authToken` field; it was only ever written
through the interface's `[extra: string]: unknown` index signature. So there is **no declared field
to remove and no type-level break** — `authTokenHash?: string` is added as a new optional property,
and that is the whole diff. `AuthResult.authToken` (the field clients actually use) is
**unchanged**, and `publicUser()` has always stripped `authToken` from responses, so a correct client
never saw it.

- **Legacy field scrub.** Records written before the upgrade still carry a raw `authToken` string in
  their JSON. `issueSession` deletes it on the next write (§1.2), so any user who logs in again is
  scrubbed automatically. For users who never return, the stale token remains in the blob — but it
  is **inert**: no session key exists for it (the old key was raw-keyed and has expired), so it
  cannot be replayed. A one-shot `scripts/scrub-legacy-tokens.ts` is *optional* hygiene, not a
  security requirement. Say so explicitly, so nobody treats it as a blocker.

**6.3 The `AuthStore` seam is NOT a breaking change for consumers.** Worth stating plainly, because
"we re-engineered the storage layer" sounds like one:

- `createNextAuthRoutes({ storage: new RedisAdapter(client) })` — **still valid, unchanged.** The
  `StorageAdapter` is auto-wrapped in `KvAuthStore`.
- All four existing adapters are **untouched**, and anyone who wrote a custom `StorageAdapter`
  against the old contract keeps working.
- The refactor is confined to `src/server/*` internals plus the new `store.ts`. The **public API and
  the client bundle do not move.**
- The only people who feel anything are *future* backend authors — who now get a port they can
  actually implement correctly.

## 9. Which databases to support, and in what order

### 9.1 The finding that should shape the roadmap

**Crypto apps do not use "crypto databases," and there is no web3-specific signal to chase.**

The stores that dominate crypto engineering conversations — ClickHouse, Databricks, BigQuery,
Snowflake, TimescaleDB — are for **on-chain analytics**: indexers, explorers, price history, chain
forensics. They are OLAP: append-oriented, no atomic point-updates, no TTL semantics. **None of them
can back this SDK.** When Dune migrated Postgres → Spark/Databricks → Trino, that was an *analytics*
migration; reading it as guidance for an auth store would be a category error.

The tell is in the templates: `scaffold-eth-2` and `solana-labs/dapp-scaffold` ship **zero
database** — chain state plus RPC is the whole stack. A database appears only when *off-chain*
concerns do (email, sessions, profiles) — and at that moment the choice is made by **Next.js
convention, not by crypto**. thirdweb's own auth example is literally
[`thirdweb-auth-supabase`](https://github.com/thirdweb-example/thirdweb-auth-supabase).

So "what do crypto teams run for auth?" collapses into "what does a TypeScript team run?" — and the
answer is unambiguous. The evidence, all from primary sources:

**Crypto companies (their own blogs / their own ATS):**

| Company | Databases | Evidence |
|---|---|---|
| **Coinbase** | *"we use a wide variety of datastores, including **MongoDB, Postgres, and Redis**"* | Own engineering blog — **direct quote** |
| **Binance** | **MySQL** (primary) + **Redis** — MySQL in 19 of 275 live postings, Redis in 11; a DBA req names *"MongoDB or MySQL… clusters, replica sets, sharding"* | Their own Lever ATS |
| **Kraken** | **PostgreSQL** core OLTP — *"scale and tune high-throughput PostgreSQL clusters… WAL, checkpoints, autovacuum, replication lag"* | Their own Ashby ATS |
| **Helius** | **Postgres** as the hot/recent operational tier in front of columnar archival | Own engineering blog |

**Our direct comparables — wallet/auth-SDK vendors, whose self-host requirements are published:**

| Vendor | Required databases | Evidence |
|---|---|---|
| **thirdweb Engine** | **PostgreSQL 14+** + **Redis 7.2+** | Official self-host docs + their `docker-compose.yml` |
| **Openfort OpenSigner** | **PostgreSQL 16** *and* **MySQL 8.4** | Their `docker-compose.yml` |
| **Web3Auth / Torus** (encrypted key-share metadata) | **MySQL** + **Redis** | Their repo's dependencies |
| **Magic** | No DB named — key material in **AWS KMS / Vault** | Their security doc |

**Postgres and Redis appear in every stack that names one.** MySQL appears in three. Nothing else
recurs. And that matches the broad baseline — Stack Overflow 2025: **Postgres 55.6%**, MySQL 40.5%,
SQLite 37.5%, Redis 28%, MongoDB 24%, DynamoDB 9.8%, Supabase 6.0%, Firestore 5.7%, CockroachDB 1.0%
(Neon, Turso, PlanetScale, and Cloudflare D1 do not register at all). Weekly npm downloads, pulled
2026-07-13: `pg` **31.5M**, `@supabase/supabase-js` **20.7M**, `ioredis` 19.0M, `mongodb` 13.6M,
`mysql2` 12.6M, `@aws-sdk/client-dynamodb` 8.6M, `firebase` 8.1M, `@upstash/redis` 3.2M,
`@neondatabase/serverless` 2.7M, `@libsql/client` 1.7M.

### 9.2 🚨 Two numbers that should change what we already ship

- **`@vercel/kv` is at 316K/week — 10× *smaller* than Upstash — because Vercel sunset it.** Vercel
  deprecated **Vercel KV** (Oct 2024) and **Vercel Postgres** (Nov 2024), replacing both with
  Marketplace integrations (Upstash, Neon). Per Vercel's own storage docs, their only remaining
  first-party stores are **Blob** and **Edge Config**. **We are maintaining an adapter for a dead
  product**, and the README still advertises it as a headline backend.
  → **Action for `0.5.0` (docs workstream, §5):** mark `VercelKVAdapter` **legacy/deprecated** in the
  README and `STORAGE_ADAPTERS.md`, point new deployments at Upstash, and keep the adapter working
  (it costs nothing — Upstash and Vercel KV share the `KvLike` surface). Note that
  `resolveStorageAdapter()` **already prefers Upstash over Vercel KV** — that ordering is now
  load-bearing rather than incidental, and should be commented as such.
- **PlanetScale is at 191K/week** — below even the two deprecated Vercel packages — and it killed its
  free tier in 2024. **Do not build a PlanetScale adapter.** MySQL support, when it comes, should
  target plain MySQL/MariaDB.

### 9.3 The ranking

Ordered by **(adoption among likely adopters) × (how cleanly the backend satisfies the contract)**.
The contract is the gate: the SDK needs **atomic `incr`**, **expiry**, **atomic get-and-delete**, and
**per-field atomic hash writes**. A store missing any of those cannot back the SDK safely, however
popular it is. Capability claims below are from each vendor's primary documentation.

| # | Backend | `incr` | TTL | `getdel` | Why, and the caveat |
|---|---|---|---|---|---|
| **1** | **PostgreSQL** → covers **Supabase, Neon, RDS, Railway, Render, Fly, and CockroachDB** (all Postgres-on-the-wire) | ✅ | ❌ none | ✅ `DELETE…RETURNING` | **The whole ballgame — one adapter, most of the demand.** Cleanest contract fit in the field. *Caveat: no native TTL, so `expires_at` + read-path filter + `sweepExpired()` are ours to build. And **Supabase's `public` schema is world-readable by default** 🚨 (MULTI_DB §4.1).* |
| **2** | **MongoDB / Atlas** | ✅ `$inc` | ⚠️ ~60s sweep | ✅ `findOneAndDelete` | 24% of developers, 13.6M/wk, and the one datastore sourced with high confidence at a major exchange (Coinbase). *Caveat: TTL is a sweeper, not expiry — plus the dotted-`appId` nesting trap.* |
| **3** | **SQLite / libSQL (Turso)** | ✅ | ❌ none | ✅ (≥3.35) | The dev + self-host story; near-free once #1 exists (same dialect family). Turso makes it network-accessible. *Caveat: local SQLite cannot back a serverless deploy; the file is a credential store — mode `0600`, never web-served.* |
| **4** | **DynamoDB** | ✅ atomic counters | ⚠️ **"within a few days"** | ✅ `ReturnValues=ALL_OLD` | A genuinely clean fit that low mindshare hides, and where AWS-native shops live. *Caveat: the worst TTL lag of any candidate — read-path filtering is non-negotiable.* |
| **5** | **MySQL / MariaDB** (**not** PlanetScale — §9.2) | ✅ | ❌ | ⚠️ **no `DELETE…RETURNING`** | Real adoption (Binance, Web3Auth, Openfort; #2 overall). But **the three worst hazards land together**: `getdel` needs an explicit transaction *or challenges become replayable*; `utf8mb4` collation traps; silent truncation. **Deliberately last.** |
| **6** | **Cloudflare Durable Objects** | ✅ | ❌ (alarms) | ✅ | The **correct** Cloudflare answer — strongly consistent and transactional. D1 is SQLite and mostly falls out of #3. Build on demand. |
| **7** | **Convex** | ⚠️ **sharded only** | ❌ **none at all** | ✅ (serializable mutations) | **Not built in `0.5.0` or `0.6.0` — but it is the backend that proved the seam was wrong** ([`ADR-001`](./ADR-001-storage-seam.md)). Serializable mutations make atomic `takeChallenge` free, and a component's writes commit *transactionally with the customer's own mutation* — stronger than anything Redis or Postgres offers. *Caveats: a naive counter is Convex's own documented anti-pattern (OCC write conflicts) and must be sharded; there is **no document TTL** whatsoever; and it is not a "point the SDK at a URL" backend — all DB access must go through functions the customer deploys, so it ships as a **Convex component**, not an adapter.* |

### 9.4 What to refuse — and say so out loud, before someone discovers it

- **Cloudflare Workers KV cannot back this SDK. 🚫** No atomic increment, no atomic get-and-delete,
  up to **60s** global propagation, and a hard limit of **1 write/sec/key**. Rate limiting would
  silently not work, and challenges would be **replayable** off a stale read. It is the first thing
  an edge-first developer reaches for and it is precisely the wrong choice. When someone asks for
  Cloudflare, the answer is **Durable Objects**.
- **"Native TTL" is a trap, not a feature.** 🚨 For **MongoDB** (~60s), **DynamoDB** ("within a few
  days"), and **Firestore** (24h — and Google's docs state plainly that *expired documents continue
  to appear in queries*), TTL is **space reclamation, not an expiry authority**. Because
  `verifySession` accepts any non-null value `get` returns, a naïve adapter on any of these
  **accepts expired session tokens** — for a minute, or for days. This is the single most important
  line to hold, and it is why the read-path expiry filter is a contract requirement rather than an
  optimization.
- **ClickHouse / BigQuery / Snowflake / Databricks / TimescaleDB** — wrong engine class (§9.1).
- **Firestore** — possible, but weak adoption and the worst TTL semantics of the lot. Not worth it.
- **CockroachDB** — no adapter needed; it speaks the Postgres wire protocol and comes free with #1.

### 9.5 The strategic consequence

**The Tier-1 work is one adapter, not six.** `PostgresAdapter` alone covers Postgres, Supabase, Neon,
RDS, Railway, Render, Fly, and CockroachDB — most of the addressable demand — and Supabase earns not
a separate adapter but a **documented preset**, purely because its default configuration is
catastrophic (MULTI_DB §4.1). `SqliteAdapter` is a small delta on the same dialect. That is why
`0.6.0` is scoped to exactly those two, and why MySQL is sequenced last rather than treated as an
equivalent line item.
